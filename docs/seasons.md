# 演出年份：每一年的光表分開存

每一年的演出各自一個 MongoDB 資料庫，帳號各年共用：

| 資料庫 | 內容 |
|---|---|
| `test` | `users`（帳號）。分年之前的 `color` / `raw_json` 也還留在這裡，沒有刪 |
| `lightdance_2025`、`lightdance_2026`… | 那一年的 `color`（韌體播的）與 `raw_json`（編輯器載回來的） |

音樂檔：新上傳的放 `music_file/_years/<年份>/<使用者>/`；分年之前上傳的留在
`music_file/<使用者>/`，**每一年都看得到**（舊光表引用的是檔名，搬走就找不到歌了）。

## 年份怎麼算

**7 月到隔年 6 月上傳的，算隔年的演出**（2026-07-01 ～ 2027-06-30 → 2027）。
分界月份是 `SEASON_START_MONTH`（預設 7），定義只在 `backend/seasons.py`——前端
不自己算，沒選年份時請求就不帶 `year`，由後端決定今年是哪一年。

## API

所有光表與音樂端點都多了一個選填的 `?year=`：

| 沒帶 `year` 的時候 | 用哪一年 |
|---|---|
| 指定版本（`/items/{u}/{版本}`、`/raw/{u}/{版本}`） | 由版本編號推（版本編號開頭就是日期），所以**分年之前的舊連結照樣打得開** |
| `LATEST`、清單、上傳 | 今年 |

另外新增 `GET /api/seasons` → `{"current": 2027, "seasons": [2027, 2026, 2025]}`。

⚠️ **韌體讀 `LATEST` 時拿的是「今年」最新的一版。** 每年 7 月 1 日一過，新的
一年還沒有人存檔之前，`LATEST` 會是「找不到」。要讀去年的就帶 `?year=`。

⚠️ **存檔存進 Dashboard 選的那一年。** 打開去年的光表修改後存檔，那一版留在
去年，不會跑到今年。存檔成功的訊息會講出存進哪一年。

## 第一次部署：把舊資料搬過去

舊資料在 `test` 裡。新版部署之後如果還沒搬，清單會是空的（光表沒有不見，只是
還在舊的地方）。所以**先搬再部署，部署完再搬一次**補上中間新存的版本：

```bash
# 0. 先備份（舊版的備份腳本只備份 test，而舊資料正好都在那裡）
cd backend && ./mongo-backup.sh && cd ..

# 1. 預覽：只印出每一年會分到幾份，不寫入
docker compose -f docker-compose.prod.yml --env-file .env.deployment \
  exec backend python migrate_to_seasons.py

# 2. 複製（只複製，test 裡的原始資料不會被刪）
docker compose -f docker-compose.prod.yml --env-file .env.deployment \
  exec backend python migrate_to_seasons.py --apply

# 3. 部署新版之後再跑一次 --apply（已經搬過的會跳過，不會重複）
```

> 第 1、2 步要在**已經包含 `migrate_to_seasons.py` 的後端容器**裡跑。如果正在
> 跑的還是舊版容器，就先部署再立刻跑第 2 步——中間那段時間清單會是空的。

在真實資料的副本上演練過（2026-11-06 的備份）：`color` 609 份、`raw_json` 625 份，
分到 2025 / 2026 / 2027 三年，沒有認不出年份的；有 4 組版本在來源裡就重複
（唯一索引之前留下的），腳本只複製第一份並把另一份的 `_id` 列出來。

## 備份

`backend/mongo-backup.sh` 會備份 `test` 加上所有 `lightdance_<年份>`（每次現場問
有哪些年份）。列不出有哪些資料庫時整次備份失敗，而不是只備份到帳號——漏掉每一年
的光表比備份失敗更糟，後者至少會被發現。還原時備份裡有幾個資料庫就還原幾個。
