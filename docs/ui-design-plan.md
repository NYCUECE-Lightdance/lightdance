## 1. 現況診斷

以下每一項都有實際量測或截圖佐證，不是感覺。

### 1.1 沒有 design token，287 個寫死的顏色

```
14 個 CSS 檔、287 個寫死的顏色值、0 個變數
rgb(49, 47, 47) × 25    rgb(150, 146, 146) × 15    rgb(237, 237, 237) × 13
#ffffff × 13            #fff × 10                  #ccc × 9
```

同一個灰有 25 個副本，白色有 `#fff` / `#ffffff` / `rgb(255,255,255)` 三種寫法並存。
想把背景調暗一階要改 25 個地方，漏一個就花掉。

**這是可維護性的主要破口**，也是為什麼這份計畫把 token 放在第一層 —— 手法跟
`constants/parts.js` 收斂 9 處 `Array.from({length: 7})` 完全一樣。

值得一提的是 `pages/Dashboard.css` **已經有一套 token**（`--bg-dark: #0b0e11`、
`--card-bg: #161b22`、`--border-color: #30363d`、`--text-muted: #8b949e`）。
所以現況是 Dashboard 有設計系統、編輯器沒有，兩邊看起來像兩個產品。

### 1.2 介面在跟燈光顏色搶注意力

編輯器畫面上目前有這些飽和色塊：橘色的「有尚未儲存的變更」橫幅、綠色的
New Project、七個藍色舞者標籤、整條佔畫面底部的綠色波形（`rgb(68, 143, 100)`）。

這是一個**色彩編輯器**。使用者要判斷的是燈光顏色對不對，但畫面上最搶眼的東西
全部不是燈光資料。放一塊 30% 透明度的紅色進去，它在一堆藍綠之中根本不顯眼。

### 1.3 光衣在未點亮時看不見

`Armor.jsx` 的 SVG 是黑色，畫在深灰底上。七套光衣在預設狀態是七團黑影，
分不出哪塊是手臂哪塊是腿，要上了色才浮出來。

### 1.4 按鈕沒有階層

Header 一排裡有**四種按鈕樣式**：outlined（Output / Shortcuts / Load / Edit / Logout）、
綠色實心（New Project）、橘色實心（未儲存警告）、icon-only（機器人）。
Logout 和 Output 視覺權重相同，但一個是破壞性離開、一個是主要動作。

工具列 14 顆圖示平鋪，沒有分組也沒有分隔線，剪刀、垃圾桶、調色盤、魔杖權重全等。

### 1.5 提示文字是英文，而且位置寫死

16 個提示全部是英文，出現在一個全繁體中文的介面裡：

```
Cut Selected Block ( C )    Previous Time Point (Shift + ←)    Switch Track
Brightness                  Playback speed                     Color( P )
Choose-Timeline             Add-Timeline
```

最後兩個更是內部命名直接外露給使用者。

位置則全部是寫死的百分比：

| 檔案 | 規則 |
|---|---|
| `ControlPanel.css` | `left: 28%` / `48%` / `68%` / `88%`（四顆按鈕各一個魔術數字） |
| `audioplayer.css` | `left: 64%` / `78%`、`top: -40px` |
| `Timeline.css` | `left: -120px`、`width: 300px` |

那些數字是照著「工具列現在有幾顆按鈕」算出來的。**任何人加一顆按鈕，全部提示
就指到錯的地方** —— 跟 2026-08-12 修掉的版面 bug 是同一個病因。

### 1.6 時間軸沒有刻度尺

整個編輯器沒有任何時間標記。30 秒的曲子要把色塊對到副歌那一拍，只能靠一條紅色
播放頭和右上角的 `0:00:000 / 0:30:000` 文字反推。

這不只是美觀問題 —— 它直接影響排燈的準確度。

### 1.7 調色盤把 debug 產物當主要 UI

調色盤正中央顯示 `84215140` / `4282069092`，那是打包後的 32-bit RGBA 整數。
對使用者沒有意義。

## 2. 設計原則（已拍板）

> **編輯器的介面應該是無彩色的。畫面上唯一飽和的顏色，應該是使用者的燈光資料。**

所有 chrome（背景、面板、按鈕、邊框、文字、波形）收斂成灰階。狀態靠**亮度**和
**圖示**表達，不靠色相。這樣色塊和光衣會自己從畫面上跳出來。

Dashboard 的深綠保留不動 —— 它是入口頁，不跟燈光顏色同框。

### 2.1 選取態用什麼顏色

無彩色介面仍然需要一個「被選中」的視覺訊號，而色塊本身可以是任何顏色，
所以選取框**必須在任何底色上都讀得出來**。

決定：**選取 = 白色外框 + 外側深色描邊**（雙層 ring）。白色在飽和色上對比最高，
深色描邊則保證在白色/淺色色塊上也看得見。不使用彩色選取框，因為它會在
「選了一塊藍色」時和色塊本身混淆。

這個決定是可逆的 —— 全部走 token（`--ring-selected`），要換只改一個值。

### 2.2 決策紀錄（2026-08-12 拍板）

以下六項已經看過互動預覽後決定，實作時直接照做，不需要再問。

| # | 項目 | 決定 |
|---|---|---|
| 1 | 灰階傾向 | **純中性**（R=G=B），不做冷偏或暖偏 |
| 2 | 光衣 | **黑卡 + 描邊**：面板維持深灰，每位舞者站在自己的黑卡上 |
| 3 | 亮度記號 | **右上角三角形角標**，只在 alpha < 100% 時出現 |
| 4 | 工具列分組 | 照第 6.1 節的六組順序 |
| 5 | 調色盤最愛色 | **6 格**（現況 4 格） |
| 6 | 軌道左側控制項 | **一直顯示**，不做 hover 才出現 |

### 2.3 一個要修正的推論：alpha 合成的誤差有多大

初版文件說「墊底盤會讓 30% 的紅變成灰粉紅，預覽系統性騙人」。方向對，但沒算過
換成新色階之後還剩多少誤差。算出來差很多：

| 底色 | 30% 亮度的紅合成後 | 與真實值的距離 |
|---|---|---|
| 現況 `rgb(70,70,70)` | `rgb(126,67,63)` | 差很遠，變成磚紅 |
| 提案面板 `#171717` | `rgb(93,35,33)` | 小很多 |
| 純黑（真實） | `rgb(77,18,14)` | — |

**光是把面板從 `rgb(70,70,70)` 壓到 `#171717`，這個問題就解掉八成** —— 誤差嚴重
是因為底色太亮，不是因為「有底色」。所以黑卡是錦上添花而非必要（仍然照決策 2 做，
因為它同時給了「一人一格」的分隔）。

真正非做不可的是**描邊**：腿和鞋子在任何底色下都是純黑，這跟底色無關。

### 3.2 收斂做法

逐檔把寫死值換成 token。同一個灰的 25 個副本會塌成一個 `--bg-control`。
過程中會發現一批「差 1–2 階但其實是同一個意圖」的顏色（`#333` / `#2a2a2a` /
`rgb(49,47,47)`），一律歸到最接近的 token —— 這種細微差異沒有設計意圖，
只是不同人不同時間各自挑的。

### 3.3 防腐測試

新增 `frontend/src/styles/__tests__/tokens.test.js`：掃描 `src/**/*.css`，
斷言**除了 `tokens.css` 以外沒有寫死的十六進位或 `rgb()` 顏色**。

沒有這個測試，token 層會在三個月內腐化回去 —— 下一個人趕時間就會直接寫
`#333`。這跟 `partsConfig.test.js` 是同一種安全網：不阻止你改，但改壞時
準確告訴你是哪一項。

例外清單（允許寫死）需明確列在測試裡並附理由，例如波形 canvas 的繪圖色
若是在 JS 裡算出來的。

## 4. 第 1 層：色彩語意

在 token 之上做語意調整，這一層只改 token 的值與少數規則。

| 元素 | 現況 | 改成 |
|---|---|---|
| 「有尚未儲存的變更」 | 橘色實心橫幅 | 灰底 + 警告圖示 + `--state-warning` 只用在圖示 |
| New Project | 綠色實心 | primary 按鈕（淺灰實心） |
| 舞者標籤 | 藍色藥丸 | 灰色藥丸，選中時提高亮度 |
| 波形 | 綠底綠波 | 灰階；波形比底色亮兩階 |
| 光衣未點亮 | 純黑（看不見） | `--armor-outline` 1.5px 描邊，顏色不受影響 |
| 光衣容器 | 七人擠在同一片灰上 | 面板維持深灰，每人一張 `--armor-stage` 黑卡 |
| 色塊選取 | 單層細框 | 白色雙層 ring |
| 色塊亮度 | 看不出 alpha | alpha < 100% 時右上角加白色三角角標 |
| 調色盤整數 | `84215140` 大字 | 移除；改成可編輯的 HEX 欄位 |
| 最愛色 | 4 格 | 6 格 |

**風險**：波形改灰階後可能和時間軸色塊混淆。緩解方式是讓波形區用比
`--bg-canvas` 亮一階的底色，並保留現有的上下邊界線，形成明確的區塊感。
這點要在瀏覽器實看確認，不能只在腦中推。

## 7. 第 4 層：時間刻度尺（唯一的 DOM 新增）

這是本輪唯一新增的結構，需要說明為什麼它不違反「不動版面」的範圍設定。

### 7.1 為什麼它很便宜

現有結構：

```
.scroll-container                       ← 橫向捲動
  └── .main-controlPanel   width: 100% × zoomLevel
        ├── <ShiftMarkers>               ← 已經是一條「浮在時間軸上的標記帶」
        ├── .timeline-container
        └── .waveform-container
```

`.main-controlPanel` 整體隨 zoom 縮放，內部一律用 `time / duration × 100%` 定位。
所以刻度尺當 `ShiftMarkers` 的兄弟節點插進去，**縮放與橫向捲動自動同步**，
不需要任何新的座標邏輯。`ShiftMarkers` 已經證明這個模式可行。

成本是一個新元件加 `audioplayer.jsx` 一行，不需要重排任何既有元素。

### 7.2 規格

新增 `components/audio/TimeRuler.jsx`：

- 高度 22px，底色 `--bg-panel`，下緣 `--border-subtle`
- 刻度密度隨 `zoomLevel` 調整：目標是**相鄰標籤至少相隔 60px**，
  依此從 `[1, 2, 5, 10, 15, 30, 60]` 秒挑最小的合適間隔
- 主刻度：全高 + 標籤 `m:ss`；次刻度：半高無標籤
- 播放頭位置同步畫一條與時間軸相同的紅線，讓兩者對得起來
- 點擊刻度尺 = 跳到該時間（與現有 `updateCurrentTime` 同一條路徑）

刻度密度用「螢幕像素間距」而不是「固定每 5 秒」，是因為縮放 8 倍時每 5 秒一格
會擠成一團 —— 這是 DAW 的標準做法。

## 8. 調色盤與軌道左側

這兩塊的決定牽涉功能取捨，不只是配色。

### 8.1 調色盤那一欄

現在 170px 寬的欄位裡塞了大色塊、`100%` 步進器、debug 整數、4 個最愛色、
填色/取色兩個標籤，彼此擠成一團。

| 項目 | 決定 |
|---|---|
| 最愛色 | **6 格**，排成 3×2 |
| debug 整數 | 移除，換成**可編輯的 HEX 欄位** |
| 亮度步進器 | 保留，但和 HEX 欄位對齊成同一欄寬 |
| 填色 / 取色 | 維持兩個標籤，只做視覺整理（改成一組明確的模式切換） |

HEX 欄位是我代為決定的：既然那個位置本來就要放「目前顏色是什麼」，
放一個看得懂又能貼上色碼的欄位，比放一個沒人看得懂的整數嚴格更好，
而且成本幾乎一樣。如果不想要輸入功能，改成唯讀顯示也行。

### 8.1.1 施工回顧（2026-08-14）——這一欄後來又改了三件事

上表的「視覺整理」做完之後，這一欄仍然有三個**行為**層面的問題，不是排版能解決的。

**點最愛色的預設行為是覆蓋。** 填色/取色的切換是一支
`<input type="range" min="0" max="1" step="1">`——用連續值的控制項表達兩個狀態，
而且預設停在「填色」那一端。也就是說，點任何一格存好的顏色都會**把它蓋成目前的
顏色**；要拿出存好的顏色，得先發現那支滑桿是個開關並把它推到另一端。破壞性的
操作不該是預設值。現在換成 `使用 / 存色` 兩顆按鈕（`aria-pressed` 表示目前這一邊），
預設是「使用」，而且空格不看模式一律是「存」——空的格子沒有東西可以拿出來用，
所以那個動作沒有歧義。

**亮度只有六段。** `-  N%  +` 三格按鈕一步 `(parseInt(A*10) ± 2) / 10`，走得到的值
只有 0 / 20 / 40 / 60 / 80 / 100% 六個；而 `Ctrl+1~9` 早就在設 10%~90%。同一個屬性
兩套精度，滑桿使用者永遠對不上快捷鍵設出來的值。改成 1% 一格的滑桿之後兩邊一致。
（順帶：那個元件的 CSS 有一條裸的 `*` 選擇器，一 import 就把 `font-family` 與
`text-align: center` 套到全站每一個元素上。元件連同 CSS 一起刪掉了。）

**空格長得像存了白色。** 沒存過的格子被補成 `{R:255,G:255,B:255,A:1}`，而白色是
最常用的燈色之一——不能拿它當哨兵。改成 `null` + 虛線框 + `+`。既有資料裡真的
存在的白色原樣保留（那是使用者存的東西，不能事後清掉）。

另外補了一排**最近使用**：顏色在 reducer 的 `UPDATECHOSENCOLOR` 裡自動記
（選色的入口有五個，每個各記一次遲早會漏），依色相去重所以拉亮度滑桿不會把清單
塞爆。使用者不必先想到「這個顏色等一下還會用到」才留得住它。

形狀與不變式集中在 `frontend/src/utils/palette.js`。順手修掉一個靜默的錯：
快捷鍵 `1~8` 走的是二維座標換算 `favoriteColor[row % rows][col]`，色票收成一列
六格之後 `rows = 1`，於是 **7 與 8 會繞回第 1、2 格**——按 7 套到的是第 1 格的顏色。
現在鍵位由 `FAVORITE_SLOTS` 推導，超出格數不做事。

### 8.2 軌道左側的資訊設計

每行五組控制項（舞者下拉、部位下拉、↑↓ 排序、刪除、顯示切換）**一律持續顯示**，
不做 hover 才出現。

理由是 hover 才出現會讓「這行到底能做什麼」變成要試才知道，
而且在軌道很多時滑鼠移動距離會變成負擔。代價是視覺較密，
靠 ghost 按鈕（無框、只有 hover 底色）把它們的視覺重量壓下來。

## 9. 這一輪不做

明確寫下來，避免範圍蔓延：

| 項目 | 為什麼延後 |
|---|---|
| 軌道行高固定 / 可縮放 | 要改 `height={100 / showPart.length}` 的語意，牽動 Timeline 的 flex 假設與拖曳座標，屬於版面重構 |
| 舞者區與裝備編輯的空間重分配 | 同上，且需要先決定裝備編輯要不要改成彈出式 |
| 舞者開關列與舞者標籤合併 | 會動 `DancerToggle` 與 `People` 的元件邊界 |
| 深色 / 淺色主題切換 | token 層做完之後才有可能，但目前沒有需求 |

第一項是我認為下一輪最該做的 —— 它對應「軌道看不到全貌」這個痛點。

## 10. 驗收與交付順序

### 10.1 驗收條件（缺一不可）

1. `npx vitest run` 全綠，且新增 `tokens.test.js` 通過
2. `npm run build` 成功
3. `npm run audit:layout` 兩種視窗尺寸皆 **0 點不到 / 0 溢出**
4. `npm run e2e` **17/17**
5. 瀏覽器實看：光衣未點亮時看得見輪廓、波形與時間軸不混淆、
   工具列六個分組讀得出來

第 3、4 項特別重要 —— 這一輪會大量改 CSS，而上一輪的經驗是
**CSS 改動最容易造成「看起來好好的但點不到」**。

> ⚠️ 跑 e2e 前若出現「編輯器一直載入不了」，先重開 `npm run dev`。
> 連續 HMR 更新之後 vite 會累積到 `/home` 載不起來，這是開發伺服器的問題。

### 10.2 交付順序（四個 commit）

| # | 內容 | 風險 |
|---|---|---|
| 1 | 第 0 層：`tokens.css` + 全面收斂 + `tokens.test.js` | 中（量大但機械，測試護著） |
| 2 | 第 1、2 層：色彩語意 + 按鈕階層 | 中（視覺變化最明顯，需實看） |

每個 commit 都要過完整的 10.1 驗收。commit 1 最大，但它是純機械替換，

## 11. 風險

| 風險 | 緩解 |
|---|---|
| token 收斂時把「其實有意圖的細微色差」合併掉 | 收斂前先跑一次 `audit:layout` 存基準截圖，收斂後比對 |
| 波形灰階化後與時間軸混淆 | 波形區底色亮一階並保留邊界線；第 2 個 commit 必須實看確認 |
| 大量改 CSS 造成控制項被蓋住 | 每個 commit 跑 `audit:layout`，這正是它存在的理由 |
| 提示改成 `bottom: 100%` 後在工具列頂端被裁切 | 檢查祖先有沒有 `overflow: hidden`；必要時提示改用 portal |
| 無彩色化之後畫面「太灰、分不出層次」 | 背景階要拉開足夠對比（相鄰階至少差 4–6% 亮度），並靠邊框而非底色區分區塊 |

## 12. 施工回顧（v1.2）

計畫寫得再細，動手之後還是會遇到只有實作才看得到的東西。這三件值得記下來。

### 12.1 收斂 287 個顏色不能用手打的對照表

長尾有 130 種寫法。手動對映一定會漏、也一定會把語意不同的值合併錯。
實際做法是**依 CSS 屬性角色決定候選 token**（`color` / `fill` 用文字階、
`background` 用背景階、`border` 用邊框階），再按亮度就近吸附，然後逐檔審 diff。

審出來兩類系統性偏差，都是機器judgement不足而人一眼就看得出來的：

| 偏差 | 後果 |
|---|---|
| `color` 被吸到 overlay token | 白色 0.9 的文字變成白色 0.08，幾乎看不見 |
| `rgb(49,47,47)`（按鈕靜止態，出現 25 次）被吸到 hover 階 | 所有按鈕看起來像被 hover |

修法是拿原始檔逐行對照改回來。**先機器再人審**比純手工快一個數量級，
而且審 diff 時注意力集中在「哪裡不對」而不是「這個值該換成什麼」。

### 12.2 兩個只有瀏覽器測得到的問題

- **`.btn` 撞到 Bootstrap。** 按鈕四階層寫好之後完全沒作用——`bootstrap.min.css`
  在 `App.jsx` 裡比 `styles/buttons.css` 晚載入，同權重下它贏。截圖一看就發現
  header 五顆按鈕全是暗灰，但單元測試不會紅。類別前綴改成 `ld-` 解決。
- **17 則提示有 12 則被裁掉。** 提示浮在按鈕正上方，`.controls` 的 `overflow`
  把它們切光了，而且**畫面上完全看不出來**（hover 就是沒東西出現，沒有錯誤）。
  `overflow-x: auto` + `overflow-y: visible` 在 CSS 裡不成立，所以改成
  「放不下就換行」，並把 `.scroll-container` 從絕對定位改成正常的 flex 項目。

第二項已經加進 `npm run audit:layout` 當永久檢查（第三項：被裁掉的提示）。

### 12.3 e2e 工具本身有三個會造成假失敗的坑

驗收跑不過的時候，先確認是程式壞了還是量測環境壞了。這三個都花過時間：

| 症狀 | 真正的原因 |
|---|---|
| 「編輯器一直載入不了」 | 開發伺服器剛啟動時第一次載入 `/home` 要轉譯幾百個模組，超過等待時限。需要暖機。 |
| 暖機之後反而更常失敗 | 暖機沒攔 `/api/**`，請求打到 vite proxy 指向的 `backend` 主機（開發機上不存在），整個伺服器接著變慢 |
| 暖機借用同一個 context 就壞掉 | 未登入開 `/home` 會把「沒有 token」寫進 persist，後面登入完再開就被那份殘留彈回首頁——本來要繞過的問題被暖機自己製造出來 |

現在 `e2e/browser.mjs` 的 `warmUp()` 用**獨立 browser + 獨立 context + 攔截 API**，
三個坑一起避開。
